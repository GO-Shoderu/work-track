# Phase 2B — public discovery and applications

FR-091–096, FR-070–075, FR-100–103. Review checkpoint only: no UI, managed Supabase changes or deployment. No new dependencies.

## Public contracts

Server-only helpers:

- `getOrganisationCareers({ careersSlug, offset?, limit? })`: organisation plus open Jobs, or null for an unknown slug. Default page size 50, maximum 100.
- `getPublicJob({ careersSlug, publicId })`: organisation plus one open Job, or null when unavailable or the identifiers belong to different tenants.

Organisation fields are exactly `name`, `careers_slug`. Careers Job cards contain only `public_id`, `title`, `teaser`, `closes_at`, `published_at`. Single-Job details additionally contain bounded `description_rich` and derived plain `description`. Strict response schemas reject detail fields on cards.

The stateless client uses only the publishable key. Narrow SECURITY DEFINER read functions enforce `published` and an absent or future closing date using database statement time. Existing table grants and authenticated RLS remain unchanged. Responses use strict schemas, including the existing bounded Tiptap schema. Text remains untrusted and must never be rendered as raw HTML.

`applyToPublicJob(input, formData)` is a public Server Action. Input is exactly `{ careersSlug, publicId, fullName, email, phone?, linkedinUrl? }`; FormData contains exactly one `file`. It enforces same origin and strict validation, returning only `{ ok: true }` or a generic error. It never returns internal Candidate/Application identifiers, email-match information, assessment output or credentials. The existing 6 MB Server Action body limit accommodates the maximum 5 MiB PDF plus multipart framing.

## CV schema and ownership

`application_cvs` stores one immutable CV association per public Application: Application/Organisation/Job IDs, normalized submitted email, generated object ID, byte size, creation time and generated Storage path. The same one-to-one record preserves the submitted contact snapshot: `submitted_full_name` (required), `normalized_email` (required), `submitted_phone` and `submitted_linkedin_url` (nullable). Full name, phone and LinkedIn retain their validated submitted values, including accepted spacing; only email is normalized. There is no extra snapshot table or backfill from canonical Candidate data. Composite tenant foreign keys and a unique Organisation/Job/normalized-email constraint reinforce integrity and duplicate prevention. There are no browser or service-role table write grants. Authenticated reads use existing Application RLS.

The existing private `candidate-cvs` bucket also holds public uploads, under a distinct four-part path:

`<organisation>/applications/<application>/<object>.pdf`

The IDs are generated by the database and never supplied by the applicant. Authenticated Storage reads require an authorised Application-CV association. Restrictive Storage guards deny browser insert/update/delete for this namespace, even within the owning Organisation. The existing three-part Candidate-CV workflow remains available to authorised recruiters. No signed/public URLs are generated.

Anonymous matching never changes an existing Candidate's profile or shared `candidate_cvs` record. Email normalization trims and lowercases conservative ASCII addresses; it does not fold dots, plus aliases or provider-specific variants. Exactly one same-Organisation match is reusable; ambiguous legacy matches fail. A new Candidate is created otherwise, transactionally with the Application. Every public Application retains its own submitted-contact snapshot, including when a Candidate is reused. New Candidate profiles are initialized from the submission with trimmed name/phone, while the snapshot retains the submitted values. Another Job can reuse that Candidate with a different Application CV and snapshot. Existing Candidate/Job uniqueness also rejects a public duplicate of a manual Application, including removed Applications.

## Submission transaction and failure handling

1. Validate applicant fields and File MIME, extension, nonempty size and 5 MiB maximum.
2. Service-only `prepare_public_application` resolves the slug + public Job ID and verifies the Job is open. It creates a private upload reservation with generated IDs, email and byte size. Durable admission limits allow at most 30 reservations per Job per ten minutes and three per Job/email per hour. Reservations expire for completion after 15 minutes. These limits precede expensive PDF processing; deployment edge/IP controls remain advisable before exposing the form widely.
3. Reuse the existing bounded native PDF parser: validate magic bytes and reject unreadable/empty PDFs. Upload to the private generated path with `upsert: false`.
4. Service-only `complete_public_application` locks the reservation, rechecks Job eligibility (including expiry after lock waits), checks the private Storage object's MIME/size metadata, and serializes same-Organisation/email reuse. One transaction creates/reuses the Candidate, inserts an Application with `source=public`, `stage=applied`, `assessment_status=pending`, and associates the required Application CV and contact snapshot in the same transaction. It never writes `candidate_cvs`.
5. Only a confirmed response with matching Application/CV IDs permits success. Register a Next.js `after()` callback and immediately return `{ ok: true }` with assessment still `pending`; provider execution does not block the applicant response.

Storage and PostgreSQL cannot share a transaction. No Application is inserted before the uploaded object is confirmed. A failed or ambiguous upload/database response returns generic failure. A timeout might follow a committed transaction, so uploaded objects are **never blindly deleted** on failure. Private unassociated objects/reservations may remain for operator reconciliation. Retrying cannot create duplicate Applications. No Candidate or historical Application is deleted.

Reconciliation must first exclude live reservations and every referenced `application_cvs.storage_path`, then remove confirmed unassociated objects through the Storage API (never by deleting Storage metadata alone). No cleanup worker or applicant retry/edit protocol is included in this phase. Keep reservations for at least the admission window and until any associated orphan is reconciled; no automated retention deletion is introduced here.

## Automatic assessment and manual compatibility

After the success response, a Next.js `after()` callback calls the existing assessment provider using the exact validated/uploaded PDF text and the Job title/plain description/content version returned by finalization. There are no live AI calls in verification. Provider output is validated with the existing result schema.

Service-only `finish_public_assessment` can finish only a pending public Application. It rechecks and locks the immutable Application CV and current Job version. A valid result sets `completed`; provider failure/malformed output sets `failed`. No assessment path changes recruitment stage or deletes an Application. Applicant success remains success when AI fails. The background provider retains its existing 45-second timeout. The installed Next.js documentation explicitly supports `after()` in Server Functions and Docker/Node runtimes. No queue or dependency was added. If callback registration fails, the confirmed submission still succeeds and remains pending for recruiter reassessment.

`candidate_assessments.cv_source` defaults existing records to `candidate`; new public results use `application`. Shared SQL validation/version checks serve the existing authenticated assessment RPC and the new service-only completion RPC. Tenant-authorized assessment reads/retries and `readApplicationCv` choose the Application CV for public Applications; manual Applications retain current Candidate-CV behavior. Candidate-CV replacement stales only manual assessments. Job content changes stale both sources and hide mismatched results under RLS.

A Job edit during AI processing leaves `stale`; results for the old version cannot be saved. A process crash or database outage after submission can leave `pending`. Recovery/retry scheduling is a later operational task; an authorised recruiter can already retry through the existing authenticated assessment action. Neither condition rolls back the Application or claims an AI result exists.
