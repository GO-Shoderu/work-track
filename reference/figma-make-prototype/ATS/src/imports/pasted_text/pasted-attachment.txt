--------------------------------------------------
PRODUCT
--------------------------------------------------

The product is a lightweight multi-tenant Applicant Tracking System.

The platform allows organisations to manage jobs, candidates and recruitment applications through a visual recruitment pipeline.

The central domain relationship is:

Candidate + Job = Application

A Candidate represents a person.

A Job represents a role an organisation is recruiting for.

An Application represents a Candidate being considered for a specific Job.

An Application has a recruitment stage.

Default stages:

- Applied
- Screening
- Interview
- Offer
- Hired
- Rejected

--------------------------------------------------
USER ROLES
--------------------------------------------------

ROLE 1 — PLATFORM OWNER / PRIMARY ADMIN

This is the highest-level platform administrator.

Capabilities:

- view a summary of the entire ATS;
- view all customer organisations;
- review prospective customer access requests;
- approve or reject customer access requests;
- create customer organisations;
- create customer accounts;
- create other Admin accounts;
- view and manage Admins;
- assign Admins to customers;
- configure or view delegated Admin privileges;
- operate within a Customer organisation on their behalf;
- review important administrative notifications;
- review sensitive administrative activity;
- review requests for high-risk operations where applicable;
- disable/archive accounts where appropriate;
- log out.

The Platform Owner should always clearly understand when they are operating at platform level versus acting inside a Customer organisation.

--------------------------------------------------

ROLE 2 — ADMIN

Admins have delegated administrative capabilities.

An Admin may:

- see Customers assigned to them;
- open an assigned Customer;
- perform permitted recruitment operations on behalf of that Customer;
- see only administrative capabilities granted to them;
- receive relevant administrative notifications;
- log out.

The UI should support the idea of granular permissions without requiring an overly complex interface.

Examples of future/delegated permissions could include:

- manage customers;
- create customer users;
- manage jobs;
- manage candidates;
- manage other Admins;
- review onboarding requests;
- access audit history.

The design should clearly differentiate between:

Platform Owner
and
Delegated Admin

without making the interface unnecessarily complicated.

--------------------------------------------------

ROLE 3 — CUSTOMER / RECRUITER

A Customer belongs to one organisation.

Primary navigation:

- Overview
- Jobs
- Candidates
- Pipeline
- Notifications, if useful
- Settings, if useful
- Logout

Capabilities:

- create Jobs;
- view Jobs;

- filter Pipeline by Job;

A Customer must never see another organisation's data.

Supporting Evidence

SECURITY-AWARE UX
--------------------------------------------------

The interface should support secure behaviour.

Examples:

- Admin organisation context must be obvious.
- High-risk Admin actions should use confirmation.
- Never make destructive actions visually equivalent to ordinary actions.
- Prefer Disable / Archive over Delete where appropriate.
- Clearly communicate role and permissions.
- Never expose sensitive security implementation details to end users.
